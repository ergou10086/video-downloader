# 任务模式检查与修正报告

> 2026-10-24 后续调度规则已调整。本文保留 2026-10-23 的检查记录；当前并发默认值、上限及网络检测功能以 [任务并发与网络自动调整](任务并发与网络自动调整.md) 为准。

检查基线：`cd98de7`、`f45acda`、`231bd68`。检查日期：2026-10-23。

## 结论

原实现已经建立了父任务队列、任务列表和独立执行器，方向合理，但尚不足以认为可靠、完整。
主要问题集中在任务生命周期、交互状态隔离、进度/结果汇总和原有全局服务的兼容性。
本次已直接修正下列问题，并补充回归测试。

## 已发现并修正的问题

| 问题 | 原实现的影响 | 本次处理 |
| --- | --- | --- |
| 启动与取消存在空窗 | 任务标记为运行后尚未建立执行器，取消可能失效或永久占用槽位 | 先登记运行上下文；取消阻止迟到的 handle 创建；父槽位等链接工作线程完成收尾后释放 |
| 停止后的完成通知丢失 | 单链接执行器提前释放 DownloadManager，后续 finish 不再通知 TaskManager | 完成通知按 generation 去重，取消和准备阶段退出也恰好通知一次 |
| 停止全部可能启动下一项 | 逐个停止的过程中调度器可能启动队列中的其他任务 | 先标记整个队列取消，再停止所有运行执行器 |
| SSE 锁顺序相反 | 重连持 SSE 锁取任务列表，同时任务回调持任务锁发布 SSE，可能死锁 | 提供不可变快照供重连读取；快照广播在任务锁外执行 |
| 进度量纲不一致 | 下载器输出 0～1，任务列表按 0～100 使用，下载中的进度接近 0% | 转成百分比，按每条链接汇总；直播使用不定进度展示 |
| 多链接没有独立执行状态 | 一个批量执行器内部串行，无法配置任务内多路直播并行 | 父任务下每条链接独立执行器、状态、进度和交互；增加任务内并行设置 |
| 结果依赖截断后的历史 | 早期失败被后面的记录挤掉；全跳过被判失败；部分失败被判完成 | 依据每条链接的最终结果汇总；失败不受日志/历史裁剪影响；跳过独立统计 |
| 排队任务使用后来的设置 | 排队期间修改分辨率、代理、密码等，改变已提交任务的行为 | 提交时固定下载配置；全局父任务并行上限和排序仍对队列实时生效 |
| 任务历史未持久化 | 任务详情有记录，全局下载历史却没有 | 任务历史回调同时写入现有 StorageService |
| 密码/归档确认不完全隔离 | 并行弹窗互相覆盖；共享 archive_prompt 被清除；单链接密码弹窗出现时任务执行器可能已经销毁 | 确认显示在各自任务详情内；用 task_id/item_id/request_id 路由；密码在原执行周期内有限重试 |
| 刷新不能完整恢复交互 | 全局只能恢复一个归档确认，密码等待可能丢失 | 待确认内容包含在任务快照中，重连后逐项恢复 |
| 共享归档改写与追加冲突 | 重下删除共享归档记录时可能丢失其他并行任务刚追加的记录 | 每个执行器使用私有归档，结束时在锁内合并增删差量，保留其他任务记录 |
| Withny 绕过任务队列 | HAR 下载及专用直播监控仍占用旧单任务执行器，不受任务并行上限控制 | 两种入口均可进入任务队列，保留各自文件选择与专用下载流程 |
| 模式切换后停止目标错误 | 关闭任务模式后，“停止”可能只停止旧执行器，遗漏仍在运行的任务 | 停止依据实际活跃任务执行；旧模式与任务队列启动互斥 |
| 更新/清理未检查任务队列 | 程序更新、yt-dlp 更新、清理临时文件可能干扰正在下载的数据和进程 | 挂起新任务启动后检查所有活跃任务；有任务时拒绝维护操作；结束后恢复 |
| 单独字幕/封面任务与队列冲突 | 工具功能可能与任务执行器同时写配套文件 | 此类独立工具运行与任务队列互斥，正常下载随附字幕不受影响 |
| 空闲退出和关闭顺序不完整 | 旧计时器回调未重新检查队列；提前关闭共享 PO Provider | 退出前重新检查队列/等待任务；先停止任务，再关闭共享 Provider |
| NicoChannel 直播和已探测直播交接识别不足 | 直播被当普通下载，优先级及直播参数错误 | 补全 NicoChannel 直播入口；已探测开播的交接任务显式传递直播身份 |
| 批量切换为单链接执行后遗漏录制时限 | Niconico 录制可能无限等待 | 单链接执行也遵守现有 LIVE_DOWNLOAD_TIMEOUT，并保留超时历史和已下载部分 |
| 频繁广播和界面重建影响使用 | 每行日志全量构造快照；输入密码、键盘焦点、日志滚动位置可能丢失 | 快照构造及推送合并至约 10 次/秒；保留输入、焦点和滚动位置；最多保留最近 100 个已结束父任务 |
| 异步列表请求覆盖更新的 SSE | 请求返回顺序不同，可能暂时把新状态恢复为旧状态 | 前端用 SSE 版本和请求序号过滤迟到响应 |
| 静态资源旧缓存 | 更新后仍运行浏览器缓存的旧脚本 | 修改资源 URL 并调整本地静态资源缓存策略 |

## 当前调度规则

- 一次开始点击创建一个父任务，多行链接和 TXT 批量也是一个父任务。
- 最大并行父任务数为 1～8，默认 1。降低上限不会强行停止已运行任务，只限制后续启动。
- 父任务排序默认 FIFO；直播优先/下载优先只改变排队任务的选择顺序，相同优先级保持 FIFO，不抢占运行中的任务。混合任务包含直播时归入直播优先级。
- 任务内直播并行数为 1～8，默认 1。为 1 时全部链接按输入顺序执行。
- 开启内部并行后，直播可以重叠执行；普通下载保持最多一路、按原输入顺序执行，并可与直播重叠。同一父任务总链接并行数也不超过该设置。
- 总执行器数量最多为两个并行数的乘积。每条链接的分片线程、限速单独生效；限速不是所有任务合计的带宽上限。
- 相同链接在一次提交中去重；已有运行或排队任务的相同链接会拒绝再次提交，避免同时写入同一输出文件。
- 归档确认仍沿用后端 20 秒默认跳过；密码确认支持提交或跳过，等待超时或重试达到上限后失败。
- “清理已结束”只清理界面任务，不删除下载文件或全局历史。任务列表最多保留最近 100 个已结束任务。

## 仍然存在的边界及后续建议

1. **普通任务队列不跨程序重启恢复。** 当前任务列表在内存中；全局下载历史和已有 WAIT 服务各自持久化。若要支持队列恢复，应单独设计任务存储、异常退出后的状态恢复和凭证重新输入，不应简单保存运行状态后自动重录。
2. **优先级是非抢占、严格优先级。** 长时间直播会持续占据父任务槽位；高优先级任务不断进入时，低优先级任务可能等待很久。需要两类任务都稳定得到资源时，可后续增加分组配额或等待时间提升优先级。
3. **不同 URL 指向同一视频/同名输出仍可能冲突。** 当前保护覆盖清理后的相同链接，不能把任意短链、别名、播放列表重叠和自定义固定文件名提前归一。大规模并发前可再增加元数据解析和输出路径预占。
4. **直播身份仍部分依赖 URL 形状。** 明确直播入口及 WAIT 探测交接已处理；普通 YouTube watch/短链等不统一执行网络探测，无法保证所有实际直播都得到直播优先级。应优先使用明确的直播入口，后续可增加任务准备阶段的元数据分类。
5. **没有新增暂停/恢复按钮、自动重试策略和全局带宽预算。** 保留底层下载器的断点续传与重试行为；这些功能需要额外状态和策略设计，不能把“取消后重建任务”视为精确恢复。
6. **长时间真实平台录制仍需实测。** 本轮覆盖本地模拟及回归，未验证各平台在线变动、会员权限、真实断网恢复、数小时封装和磁盘耗尽情形。
7. **私有归档在执行器结束时合并。** 程序被强杀时，尚未合并的新归档记录可能留在临时文件中；已下载文件和之前的共享归档不因此删除。若要保证崩溃后的归档连续性，应为会话增加恢复日志。
