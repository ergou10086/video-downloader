# 直播录制 P2/P3 实现与验证

实现日期：2026-10-24。范围为单条 URL、批量 URL 和任务队列中的直播录制；保留既有点播路径。

## 使用

1. 安装外置录播姬：`python scripts/install_bililive.py dependency/BililiveRecorder-CLI-win-x64.zip`。当前工作区已安装，无须重复解压。安装器拒绝覆盖已有安装。
2. 设置 → 直播设置 → 选择「自动（B站优先录播姬）」或「BililiveRecorder（仅B站）」。旧配置仍保留原来的 yt-dlp 选择。
3. 录播姬输出原始 FLV，登记弹幕 XML；不执行普通下载的 MP4 转封装、嵌入封面等后处理。需要代理、浏览器 Cookie、自定义 yt-dlp 参数、画质/编码筛选或音频处理时，明确降级至 yt-dlp，保留这些设置的作用。
4. 直播超时对所有 URL 直播生效。停止请求立即返回；后台先收尾、再验证，期间保留任务槽位。关闭程序采用最长约 45 秒的有界收尾等待；超大文件验证超过该时限时，重启后会补记中断报告，不能把它视为验证成功。
5. 下载页展示实际引擎、降级、分段和报告入口。重新连接页面后从磁盘恢复最近 20 个会话。报告 API 需要本机会话认证，且只接受 32 位十六进制 job ID。

## 工程边界

- `live/runner.py` 统一生命周期；`engines/` 只处理引擎命令和控制接口；`session.py` 负责原子持久化与查询；`integrity.py` 负责独立文件证据。下载执行器和并发队列复用该服务。
- 会话保存在 `download/.live-jobs/<id>/`。每次受控重试新建 `media/part-001`、`part-002`，保留退出码和原因。兼容音视频轨的分段可生成 `joined.mkv`，原始分段始终保留；重启导致的潜在缺口不会因拼接成功而消失。
- 只做文件级记录，没有自研 HLS 分片账本。`complete` 指本次录制区间的文件检查通过；`segment_completeness_verified` 始终为 `false`。不承诺平台提供了完整开播内容。
- 检查包括文件大小、容器、轨道、全文件包时间戳、首尾各 10 秒解码。不会把首尾采样描述为全片逐帧解码。低帧率视频按帧率调整间隔阈值，音频超过 1 秒的包间隔会被报告。
- 退出码 0、可播放、Webhook `SessionEnded` 三者都不能单独决定成功。空文件、缺轨、异常退出均不能显示成功；首尾解码诊断、重试、强杀、Webhook 收尾未确认或时间轴缺口会显示报告警告/缺口。
- 追开播输出使用 `from_earliest_available`，保留平台最早可用范围的限制；P4 的 DVR 能力证明不在本轮内。
- 用户停止、到时停止、失败和部分录制分别呈现；损坏文件不会因用户点了停止就变为成功。
- 重启发现原进程已经消失的未结束会话时，补记 `application_interrupted` 失败报告，保留文件，不自动拼接到新的直播场次。
- 现有 Withny YAML 多频道 `watch` 是独立监控功能，本轮没有把任意外部 YAML 输出目录纳入 URL 会话验证；不要将其旧版停止提示当作本轮完整性验收结论。

## 可靠停止与资源限制

- Windows 为每个录制子进程创建独立隐藏控制台。短时隐藏 PowerShell 辅助进程附着到目标控制台发送 Ctrl+C，避免 GUI 没有控制台或多个任务互相接收信号。等待收尾，超过时限才结束进程树。
- 录播姬先通过 Basic Auth 的 loopback REST API 关闭 `autoRecord` 并调用 `/api/room/{id}/stop`，再停止 CLI。端口由操作系统随机分配，每个进程独立认证。预留端口存在短暂绑定竞争，启动失败会安全降级。
- Webhook 每个任务一个 loopback 接收器，使用独立随机 URL token，拒绝浏览器 Origin、越界路径、错误房间和过大请求体；按 `EventId` 去重。允许 `FileClosed` 先于 `FileOpening`、`SessionEnded` 先于 `FileClosed`。选择独立接收器是为了不依赖产品 HTTP 服务的启动顺序和端口。
- 默认 60 秒无媒体增长/下载进度告警，两倍时间后按策略收尾；yt-dlp 最多重试 2 次。录播姬自行重连，已有媒体后的 CLI 崩溃直接失败，不偷偷切换引擎。
- 磁盘预检为「估算码率 × 预计秒数 × 1.3」，下限为安全余量。不限时先估算 15 分钟，运行中持续检查余量。码率是可配置估算值，不能等同于平台真实码率。
- 会话命令遮盖 Cookie、密码、代理和认证头等值，URL 去除敏感查询参数。CLI 原始临时日志结束后清理，只保留脱敏事件记录。不会上传 Cookie、录制文件或第三方二进制到 Git。

- 指定房间 `1724776963` 进行 30 分钟实录；同时对开播短号 `6`（真实房间 `7734200`）做独立短录，验证停止互不干扰。详细结果见本节后续实播记录。
- 断网测试使用仅属于测试子进程的本地代理，模拟 60 秒不可用，不修改系统网络和代理设置。
- PyInstaller 冻结版发布及完整平台矩阵仍属于发布门禁；本轮源码测试不能替代冻结版实测。弹幕 XML 只登记，不导出 SRT/ASS（P5）。

### 真实数据结果

- 指定房间持续运行 30 分钟后正常收尾，CLI 退出码 0；媒体大小 **1,851,505,601 字节**、时长 **1795.829 秒**。视频 107,750 包、音频 84,180 包，最大 DTS 间隔分别为 0.017 秒和 0.022 秒，没有倒退。首部存在参考帧解码诊断，因此当前检查器结论为 `gaps`，没有显示成功。
- 首轮数据暴露出连接准备耗时约 4 秒被计入时限；已将计时起点修正为首次媒体增长，并加入时间推进/文件增长测试。没有将修正前的数据写成“媒体时长误差小于 2 秒”；更改后的 30 分钟媒体时长精度仍需发布前再跑一次。
- 双房间短录的短号 `6` 由官方 get_info API 确认对应 `7734200` 且正在直播。独立 token、端口、目录与停止均正常，未中止指定房间长录。
- 断网实验首次未经过代理（连接计数 0），明确作废。随后在添加房间前通过官方 `/api/config/global` 设置 `optionalNetworkTransportUseSystemProxy`，实际代理统计 **14 个连接、10 次拒绝、52,408,399 字节**，中间阻断 60 秒。
- 恢复后保持同一个应用会话和 CLI 进程继续录制，未创建重复产品任务。录播姬内部产生了两个原生 `SessionId` 和两个 FLV；不能声称底层原生 SessionId 保持不变。两个文件通过探测并生成有效 `joined.mkv`，原始分段保留，报告包含 `native_recording_timeline_gap`，结论 `gaps`。
- 媒体、原始 CLI 日志、浏览器截图、临时代理脚本和测试工具在验收后清理；只保留本说明中的脱敏结果及永久自动化测试。
