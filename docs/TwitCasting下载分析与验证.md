# TwitCasting 下载分析与验证

验证日期：2026-10-23。样本为用户授权的录播 `841609706`。密码、Cookie 内容和带签名的播放地址均未写入本报告或源码。

**1. 页面上的那段提示，为什么经常出现？**

原提示属于静态平台说明。前端只要识别平台为 TwitCasting，就显示整个提示框；显示条件没有读取 HTTP 状态、下载器选择或重试结果。因此，看到“m3u8 返回 400……多初始化片段……”这段话，不能据此判断本次实际发生了 400 或进入降级。已将提示改成正常录播下载行为说明，具体失败仍由任务日志报告。

**2. 真正能够稳定复现的问题是什么？**

这条录像的媒体清单包含 2,023 个媒体分片、2 个不同的 `EXT-X-MAP` 和 1 次 `EXT-X-DISCONTINUITY`。第二个初始化段出现在 3,600.021 秒附近；媒体清单总时长为 4,045.921 秒。

旧流程先交给 yt-dlp 原生 HLS 下载器。它扫描到媒体分片之后出现另一个初始化段时，会直接报错：

```text
Initialization fragment found after media fragments, unable to download
```

使用项目现有的 `yt-dlp.exe` 和 Firefox 登录状态实测，旧路径约 5 秒后稳定出现该错误，尚未下载完整视频。这是此清单结构触发的确定性限制，与密码是否正确是两件事。上游已有相同的 [TwitCasting 多初始化段问题记录](https://github.com/yt-dlp/yt-dlp/issues/5497)。

旧执行器收到错误后，再启动一轮 yt-dlp、重新加载 Cookie、提交密码、解析播放地址，然后才加载并发插件。这样让正常的长录播下载依赖一次预期失败和整条任务重试。跨小时录播中出现这种清单时，就会反复表现为“总在降级”。本样本在一小时处切换初始化段，支持这一解释；不能据单一样本推断所有录播都采用相同分段方式。

**3. 为什么现有并发插件仍不够稳定？**

- **Windows 本地路径存在实际故障。** 旧插件用 `Path.as_uri()` 生成本地清单地址。工作区路径包含空格时，地址中的空格被编码为 `%20`；FFmpeg 的 file 协议没有将其还原，而是寻找带字面 `%20` 的路径。完整下载后实测出现 `No such file or directory`。已改为 FFmpeg 可直接读取的绝对文件路径，同时保留空格和中文。
- **缓存缺乏完整性验证。** 旧逻辑复用所有非空文件，没有记录完整长度、哈希或清单结构。截断、损坏或旧清单遗留的文件可能混入续传。新版缓存按清单结构区分，并记录已完成文件的长度和 SHA-256，续传时重新校验。
- **失败会静默改变下载策略。** 旧插件捕获所有异常后恢复远程 URL，交给 FFmpeg 串行下载。用户可能已经并发下载很久，却又开始一次慢速远程读取。新版对特殊清单显式进入兼容路径；网络错误耗尽重试后保留完整缓存并报告失败，避免隐式串行重下。
- **调度与线程设置不一致。** 旧实现一次性提交全部资源，并将线程数封顶为 16；界面实际允许 32。新版使用最多两倍线程数的待处理窗口，支持配置中的 1–32 个线程，遇到致命错误会停止继续调度旧地址。
- **清单处理不完整。** 旧插件拒绝主清单，没有利用最终重定向地址解析相对资源地址。新版只解析选定的一条变体链，用最终 CDN 地址作为资源基址；普通清单复用已经取得的媒体清单，减少重复请求。

**4. m3u8 的 400，究竟能确认到什么程度？**

本次分别验证了 cookies.txt、Firefox，以及不导入登录 Cookie、仅提交视频密码的方式，三者都成功取得样本播放清单。再次解析同一录像后，旧媒体清单仍可读取。没有复现真实的 HTTP 400，也没有证据认定这条录像必须依赖 Firefox 登录。

HTTP 400 出现在播放清单请求阶段；多初始化段限制发生在已经拿到清单之后。旧实现将两类问题写进同一个提示框，并主要通过切换直连和 Firefox 处理 400，缺少刷新当前会话播放地址的步骤。

地址过期、签名参数不正确、请求出口或会话不一致，均属于需要结合失败现场排查的方向。上游曾记录过同时请求多路 TwitCasting 播放列表会使地址失效的[历史案例](https://github.com/yt-dlp/yt-dlp/issues/382)，但该记录不能证明当前样本或账号仍有同样限制。本次没有据此修改全局任务并发或强制串行化其他任务。

新版针对主清单 400，先在当前提取器和 Cookie 会话中重新取得地址一次；针对分片请求的 400/401/403/410，先停止旧地址调度，再通过当前 yt-dlp 会话刷新一次相同格式的播放地址。刷新次数有上限，不会循环重试。未能恢复的主清单错误仍可进入现有执行器的受控网络恢复流程。该机制通过模拟错误验证；真实 400 的根因仍未得到现场验证，不能承诺所有 400 已被消除。

**5. 改写后的正常下载路径**

1. 沿用 yt-dlp 的密码鉴权、Cookie、代理、超时、元数据及下载归档流程。
2. TwitCasting 录播在首次下载前检查所选清单，直播路径保持原行为。
3. 普通清单使用原生 HLS 并发下载，并复用已取得的媒体清单。
4. 多初始化段清单直接进入有界并发下载；遵守下载线程数和限速，逐个提交完整分片及其校验记录。
5. 全部资源就绪后，FFmpeg 从本地清单复制封装，不进行视频重编码。
6. 成功后清理本次分片缓存；下载或封装失败时保留可校验的分片供下次续传。

字节范围、尚未结束或缓存器不支持的加密清单，才显式使用远程 FFmpeg 兼容路径。插件缺失时保留原有错误检测及重试兜底。`--skip-download` 和模拟运行不会触发媒体预取。其他平台不注入本录播规划器。
