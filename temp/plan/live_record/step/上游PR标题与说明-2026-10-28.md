# 上游 PR 标题与说明

适用范围：向 `maomaoyexi/video-downloader:main` 提交本 fork 主分支的整体改动，包含本轮开始前未合并的 19 个提交，以及本轮工具修复、Rplay 计划和审计文档提交。不要仅用“修复音频工具”概括整批改动。

建议先创建 **Draft PR**。下方标题和正文可直接使用。正文不承诺未完成的验收；Rplay 仅列为规划。

## 推荐标题

```text
feat: 增加多平台直播录制、弹幕导出与任务并发，修复实用工具
```

## 推荐正文

```markdown
本 PR 将直播目标识别、等待开播、实际录制、分段恢复和完整性检查接入现有下载工具，并补充直播评论采集与字幕导出、任务并发、TwitCasting 下载修复和实用工具修复。

### 直播录制

- 区分自动、从当前时刻、条件追开播与蹲开播；不支持的组合给出原因。
- 增加 URL 分类、直播状态探测与 SQLite 持久化 WAIT；处理取消、重复触发和重启时的不确定派发状态。
- 增加录制会话、优雅停止、超时、磁盘检查、无增长检测、有界重试及完整性报告；失败或缺口保留分段。
- Bilibili 优先使用外置 BililiveRecorder；Withny 复用专用录制器及原生聊天，Niconico 沿用媒体授权和 keepSeat。
- YouTube DVR 和 Twitch 本场增长 VOD 按证据尝试追播；只有码流、重叠及逐轨包序列验证通过才拼接。

### 评论、设置与 UI

- 接入 Bilibili XML、YouTube live_chat、Twitch IRC、TwitCasting WebSocket、NicoChannel 历史轮询、Niconico NDGR 和 Withny 原生聊天。
- 提供逐平台默认抓取开关、SRT/ASS 导出、匿名化、时间微调与重新导出。
- 评论进程与媒体隔离；独立报告评论缺失、重复、溢出、失败及同步可信度。
- 增加直播前检查、WAIT/录制报告入口和任务状态展示；估算时间轴不显示为已验证精确同步。

### 任务、平台修复与工具

- 增加任务列表、任务间及直播/普通下载分别控制的并发额度；密码和归档确认归属具体任务。
- 重构 TwitCasting VOD 并发下载，修复插件目录、直播降级和密码传递；密码持久化默认关闭。
- 增加网络诊断和普通下载限速配置。
- 修复音频转换页面与后端接口不一致；统一转换、响度和音量工具的路径、编码器、取消、结果验证与错误提示。
- 修复中文/空格/相对目录和 UTF-8 BOM 链接文件；递归处理保留子目录，临时清理保护可恢复直播分段。
- 增加依赖锁、许可证记录和源码/冻结版检查入口。Rplay 在本 PR 中仅提供后续接入计划，没有增加已支持平台。

### 验证

- 当前全量回归：622 passed、51 subtests passed；1 个耗时断网测试默认跳过。
- 新增音频服务行覆盖率 92%；真实 FFmpeg 验证 9 种输出格式、双次响度、静音、中文路径、同名子目录、坏输入和取消/源文件保护。
- 真实 WebUI 验证三个音频工具的启动、产物、按钮状态和错误提示；JavaScript 语法检查通过。
- 既有实播包括 Twitch 评论与媒体故障隔离，以及 NicoChannel、Niconico、Withny 的媒体/评论样本；具体时长、数量和边界见验收记录。
- 既有 90 秒完整本地 HLS HTTP 中断恢复测试、真实媒体逐包拼接及冻结程序自检通过；这些是既有验证，本轮未重新执行全部长时/冻结测试。

### 尚未宣称完成

- 全平台整场评论同步误差小于 2 秒。
- 每个平台公网广告、删档、长场、WAIT 提前/延迟、重启及完整断网的全部组合。
- Twitch 公网增长 VOD 与实时尾部的同场无缝追播闭环。
- NicoChannel 短期 JWT 的无人值守续期；部分密码/会员/礼物场景的真实样本验证。
- Bilibili 改用 yt-dlp 时的独立评论采集、Twitter/X 评论，以及 CLI 与 WebUI 全套直播流程一致性。

提交前仍需按正式 spec 构建本轮版本并完成发布检查；上游 CI 与维护者审核通过后，再根据接受的支持边界将草稿转为正式 PR。
```

## 提交范围与审查建议

- 基线已包含上游 v2.6.0 的合并结果；PR 使用上游 `main` 作 base、fork `main` 作 head，不要向自己的 fork 创建同仓库 PR。
- 标题描述最终功能，不必逐个罗列历史提交消息。若维护者采用 squash，可使用推荐标题作为合并提交标题。
- 历史未合并提交中已经存在 README 差异。本轮遵照要求没有修改 README，也没有重写或撤销这些历史提交。不要在 PR 里声称整体差异完全不含 README。
- 如果维护者要求拆分，建议依赖顺序：①任务并发与交互；②直播生命周期及录播姬；③评论/时间轴/追播；④网络诊断与工具修复。功能之间有容器和 UI 接线依赖，不能只按提交标题盲目 cherry-pick。
- Rplay 规划可由维护者决定是否随代码保留；它不构成 Rplay 已实现的证据。

详细能力结论与测试边界见 [本轮审计](直播能力与上游提交审计-2026-10-28.md)。
