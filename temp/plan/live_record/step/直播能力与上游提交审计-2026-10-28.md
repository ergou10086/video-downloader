# 直播能力、小工具与上游提交审计

日期：2026-10-28。审计基线：`2f3ab28`，本轮开始时比最新获取的 `upstream/main` 多 19 个提交。评估对象包括直播代码、设置/API/UI 接线、既有实播记录及本轮回归；本轮没有重新进行各平台长时间公网录制。

## 结论

直播主体已落地，具备提交上游草稿 PR 的价值；不能宣称整个直播计划或 P6 全部验收完成。P0–P3 的主要生命周期、WAIT、会话与录播姬集成已经实现；P4 是有条件追播和严格拼接，P5 已有七个平台评论来源，P6 仍有真实场景和发布验证缺口。

“核心功能已实现”“在某个真实直播样本通过”“所有平台各种条件都通过”是三个不同结论。目前前两类已有充分成果，第三类尚未成立。

## 尚未完整验收的内容，是否值得继续

| 优先级 | 缺口 | 价值与建议 |
| --- | --- | --- |
| 高 | 每个平台自己的媒体/评论断网、重启与正常结束验证 | 值得做。当前有共享 90 秒真实本地 HLS 故障测试、确定性平台状态矩阵及部分公网评论故障，但它们不能替代平台自身的鉴权、心跳、CDN 行为。先覆盖日常平台的录制/评论独断、共同断网、重启；不必等待所有稀有组合才发草稿 PR |
| 高 | NicoChannel 长场登录过期、B站 fallback 无评论的明确提示 | 值得做。属于用户容易遇到的失效条件。续期必须确认授权和令牌轮换，不能盲目消耗浏览器刷新凭据；fallback 应在启动前和报告中清楚说明评论来源不可用 |
| 高 | 发布程序与源码、外置依赖及私有路径一致性 | 正式发布前必须做。既有冻结构建与自检通过；本轮新增工具代码完成源码回归和真实页面检查，尚未重新构建冻结程序。上游发布时应按正式 spec 再构建并检查便携目录 |
| 中 | 整场字幕/评论误差小于 2 秒 | 值得按平台逐步做，特别是经常观看的 Withny/Nico 系列。需要可靠媒体时钟、多个分散锚点和广告/断线边界；没有依据时保留“估算/未确认”。不是所有平台都能用同一算法保证 |
| 中 | Twitch 公网同场 VOD + 尾部追播 | 常用 Twitch 追播时值得做。当前真实编码文件的逐轨完整包序列拼接验证已通过，但尚缺公网全过程。失败时保留分段，应继续禁止无证据拼接 |
| 中 | 2 小时以上长场、广告、删档、WAIT 真实提前/延迟 | 值得分层补充。先做常用平台长场和真实开播；广告/删档需真实事件或受控样本，未出现不能算通过。全平台 24 小时笛卡尔积成本很高，不应无期限阻塞已声明边界的首版 |
| 中 | 普通任务队列重启恢复、CLI 与 WebUI 直播生命周期统一 | 若需要无人值守或 CLI 使用，值得做。WAIT 已持久化；普通任务列表目前仍主要在内存中。CLI 直接走 yt-dlp，不具备 WebUI 全套会话、报告与评论流程，需明确支持范围 |
| 低/按需 | 所有会员/密码/礼物组合、X 评论、额外备用录制栈、自研 B站 WebSocket | 有真实需求和合法样本再做。B站默认继续原生 XML，避免重复协议与连接；X/Spaces 评论不能为了表格齐全而引入不适合的采集栈 |

P4 包级拼接的源码实现和本地真实媒体验证已落地；“所有平台都能追到开播且无缝拼成整场”没有完成，也不应作为无条件承诺。

## UI/UX 已覆盖与限制

已经接线：直播前检查、WAIT 列表/取消、任务并发、直播模式/超时/重试/磁盘、七个平台评论默认值、匿名化、SRT/ASS、偏移和重新导出、录制报告与同步可信度。评论失败和媒体失败分开报告。

本轮在隔离的真实 WebUI 检查了设置入口和七个平台评论开关，以及三个音频工具的启动、产物、按钮恢复和错误提示，浏览器无 JS 错误。音频表单和开关补充标签与键盘操作。

仍需完善：B站引擎切换条件对评论可用性的前置说明、NicoChannel 登录即将失效的可见提示、Withny 专用配置路径的引导，以及部分通用设置开关的键盘可访问性。不能因为接口和 DOM 测试通过，就称为所有小屏/读屏/平台权限弹窗均完成了人工验收。

| 音量调整 | 有限数字/范围校验，限幅器关闭自动增益补偿，避免抬高限幅上限；文案区分采样峰值和编码后真峰值 |

| 打开下载/日志目录 | 以应用根目录解析相对路径、去除成对引号并校验目录；保留原有目录创建行为 |

三个音频工具共用独立 `AudioToolService`：统一路径、扫描、格式、任务占用、按类型停止、暂存发布和结果事件；递归保留子目录并排除历史输出，已有文件跳过。可删除源文件的转换先验证音轨并完整解码输出；失败和取消保留源文件，默认每次运行不自动勾选删除。

FFmpeg 滤镜行为参考 [官方滤镜文档](https://www.ffmpeg.org/ffmpeg-filters.html#loudnorm)及[官方 loudnorm 实现](https://github.com/FFmpeg/FFmpeg/blob/master/libavfilter/af_loudnorm.c)，而非自行推导响度测量格式。格式相同只表示输出容器/编码选择，不代表有损来源变为无损音质；APE 解码输入可转换为 FLAC，但没有 APE 编码器时明确拒绝“保持 APE”。

## 是否可以向上游发 PR

**可以先发 Draft PR**，用途是让维护者审查已有核心实现和支持边界。建议标题聚焦“多平台直播录制、弹幕导出与任务并发”，不要写“完整支持所有直播平台”。

原计划把逐平台完整矩阵和精确同步列为 P6 发布门槛，因此目前不能宣布 P6 验收完成。如果上游接受首版明确保留这些限制，可在回归/CI、正式打包和维护者审核通过后合并；若坚持原计划全部门槛，应继续保留草稿。

这批提交跨度较大。可以提交一个整体草稿，同时在描述里按直播、任务/并发、TwitCasting、诊断/工具列出审查范围；若维护者要求拆分，再基于依赖顺序拆 PR，避免现在重写主分支历史。Rplay 本轮只有计划，不应出现在“已兼容平台”列表。
